# 站点/监控信息架构重构：监控总览为主（设计）

- **日期**：2026-06-14
- **Issue**：#76
- **方案**：A（监控中心为主页）

## 1. 背景与问题

当前 IA 围绕"单次质量测试为主、定时监控为附加功能"搭建，但产品实际主功能已变为**定时拨测监控**。由此产生三处反人类的路径：

1. **新建断裂**：在 `/sites` 弹窗建好站点后，必须再点进该站点 → 找到「持续监控」tab → 单独建任务。"我想监控这个接口"被拆成两次独立操作。
2. **定时任务身份分裂**：它既是顶部导航的独立入口 `/tasks`（跨站点只读总览），又是站点详情里的一个 tab，用户分不清"监控属于站点还是独立的东西"。
3. **模型三处配置**：全局模型库（`/settings/models`）、站点绑定模型（站点·配置 tab）、任务级再选一遍（持续监控 tab），同一个模型要碰三个地方。

**根因**：信息架构仍是"单次测试为主"的旧心智模型，与"监控为主功能"的现实错位。

## 2. 设计目标

- 让"监控是主功能"在 IA 上立起来：一进门就是监控运行态。
- 两种用户都顺：①只想监控 ②想先单次测试再决定是否监控。主路径偏监控。
- 消除三处具体摩擦：新建断裂、任务身份分裂、模型三处配置。
- 可分阶段落地，控制改动风险。

## 3. 非目标（YAGNI）

- 不引入告警"静音/snooze"功能（监控总览中 `[静音]` 仅占位讨论，本次不做）。
- 不改动告警评估算法（连续两轮防抖逻辑保持不变）。
- 不改动后端数据模型核心结构（`profiles` / `scheduled_tasks` 关联关系不变）。
- 不做模型库的权限体系重构。

## 4. 导航与路由

### 顶部导航

```
[监控总览]   [站点]   [历史与对比]        ⚙设置   👤用户
 ↑ / 默认着陆
```

`定时任务` 一词从顶导消失，升级为主着陆的 `监控总览`；`站点` 退到第二位作为管理区。

### 路由变化

| 路由 | 组件 | 说明 |
|------|------|------|
| `/` | （重定向） | → `/monitor`（原 → `/sites`） |
| `/monitor` 【新】 | `MonitorView.vue` | 监控总览/告警中心（运行态主着陆） |
| `/sites` | `SitesView.vue` | 站点管理区（健康展示瘦身） |
| `/sites/:id` | `SiteDetailView.vue` | 站点详情（tab 重排） |
| `/history` | `HistoryView.vue` | 不变 |
| `/tasks` | （重定向） | → `/monitor`（保留旧链接兼容） |
| `/settings/*` | 不变 | 模型库内容调整（见 §8） |

`/tasks` 做 301 重定向而非直接删除，避免飞书告警卡片等存量跳转链接失效。

## 5. 监控总览 / 告警中心 `/monitor`（运行态主着陆）

定位：**只看、只响应告警，不做配置编辑。** 一进门回答"我的监控现在健康吗？谁出事了？"

页面结构（自上而下四块）：

1. **顶部状态条**：`🔴告警中 N  🟡降级 N  🟢健康 N  ⚪未测 N`，右侧全局时间范围（1h/6h/24h/7d）+ 刷新。
2. **当前告警区**：有告警时显眼展示每条（站点×模型、成功率、连续轮次、所属任务、相对时间、`[进站点]`）；无告警时收起成一行"✅ 一切正常"。
3. **站点×模型健康总览**：复用现 `/sites` 看板的 site×model 表（可用性柱状、成功率、TTFT、趋势、下次拨测），搬家至此当主角。
4. **监控任务跑批状态**：现 `/tasks` 表内容，降级为**默认折叠**区（任务名/站点/频率/上次结果/下次执行/暂停·恢复·立即跑）。

**关键约束**：编辑任务不在本页进行——一律回站点详情的「监控」tab。维持"监控总览=看，站点=配"的分工。

## 6. 站点管理区 `/sites`（管理态，瘦身）

回归"管理清单"而非"健康看板"：

```
站点名       目标地址          模型数   监控    操作
aihezu-aws   api.xxx.com/v1   3       🟢开    [进入→]
test-azure   azure.xxx.com    1       ⚪关    [进入→]
```

- 保留：站点名 / 目标地址 / 模型数 / **监控开关状态** / 进入。
- 移除：可用性柱状图、TTFT、趋势等运行态指标（已移至监控总览，消除两个健康表打架）。
- `监控` 列一眼看出该站点是否已挂监控；未挂的引导去开启。

## 7. 站点详情 `/sites/:id`：tab 重排

```
现在：[概览] [配置] [性能测试] [持续监控]
改为：[概况] [监控] [单次测试] [配置]
        默认↑
```

- 顺序调整：`监控` 提到第二、紧跟概况（主功能靠前）；`单次测试`（原"性能测试"）后移；`配置`（连接信息/Key）放最后（低频）。
- **`监控` tab**：原"持续监控"，本站点监控任务在此建/改/暂停——"配监控"的唯一正式入口。
- **`配置` tab**：连接信息（地址/Key/绑定模型/改名/删站点），低频维护。
- 默认落 `概况`（单站点健康概况），与列表"进入"动作连贯。

**收益**：原"站点设置 vs 定时任务设置两个入口"问题消解——二者成为同一详情页内相邻的两个 tab（`监控` 紧挨 `配置`）；跨站点批量看则去顶部 `监控总览`。

## 8. 新建站点 → "下一步"引导

```
[+ 新建站点] 弹窗（连接信息：站点名*/目标地址*/API Key*/绑定模型*）
   → [创建站点]
   → 创建成功 → 弹引导卡片：
        "✅ 站点已创建。要现在为它开启持续监控吗？（推荐）
         不开监控就只能手动单次测试。"
        [开启监控 →]      [以后再说]
```

- **[开启监控 →]**：跳转该站点 → 监控 tab → 新建任务表单，**预填**默认值（频率默认 10 分钟、模型默认全选已绑定模型），减少二次填写。
- **[以后再说]**：留在站点详情概况页，顶部挂**常驻提示**"尚未开启监控 → 一键开启"，随时可回头开启。

## 9. 模型配置归并（三处 → 一处定义）

明确三层各自角色，消除"同一模型填三遍"：

| 层 | 角色 | 谁维护 |
|----|------|--------|
| 全局模型库 `/settings/models` | **价格/参考层**：模型有哪些、输入/输出单价（算成本用） | 管理员，普通用户基本不碰 |
| 站点·配置 tab | **唯一定义层**：本站点服务哪些模型，选一次；库里没有的可内联新增并回写全局库 | 用户 |
| 监控任务 / 单次测试 | **勾选层**：从站点已绑定模型里勾子集，默认全选 | 用户 |

- **核心规则**：模型只在站点配置层认真定义一次；任务与单次测试均退为"从站点模型勾选，默认全选"。
- 砍掉任务层内联"自定义新增模型"入口（想加模型回站点配置加），避免任务里造出站点没有的模型。

## 10. 数据流与后端影响

- **数据模型不变**：`profiles`（站点）与 `scheduled_tasks`（任务，`profile_ids` JSON 引用站点 + `configs_json` 存测试参数）关联关系保持。
- 主要为前端路由 / 视图 / 组件层重构；后端基本无破坏性变更。
- `/monitor` 所需数据（站点×模型健康、当前告警、任务跑批）应能复用现有接口（健康看板数据、`scheduled_tasks` 列表、`alert_state`）；如需聚合端点，实现计划阶段评估。

## 11. 错误处理与边界

- `/tasks` 旧链接 301→`/monitor`，确保飞书卡片跳转不失效。
- 无站点 / 无监控任务时：监控总览各区给空态引导（"还没有站点，去创建"）。
- 新建引导卡片"开启监控"跳转时若站点无可用模型，给出提示而非空表单。
- 站点删除后，监控总览中该站点相关行与告警应同步消失（沿用现有级联）。

## 12. 测试策略

- **E2E**：①新建站点→走"开启监控"引导→任务创建成功；②`/tasks` 重定向到 `/monitor`；③监控总览展示告警与健康表；④站点详情 tab 顺序与默认 tab。
- **单元/组件**：监控总览四块的渲染与空态；站点列表瘦身后列字段；模型勾选默认全选逻辑。
- 复用并迁移现有 `/sites` 看板与 `/tasks` 的既有测试，避免回归。

## 13. 落地阶段建议（实现计划阶段细化）

1. **阶段一**：路由骨架 + `/monitor` 新页（搬运现有健康表 + 告警 + 任务折叠）+ `/tasks` 重定向。
2. **阶段二**：站点列表瘦身 + 站点详情 tab 重排。
3. **阶段三**：新建站点"下一步"引导 + 监控表单预填。
4. **阶段四**：模型配置归并（站点定义层 + 任务/测试勾选层 + 砍任务内联新增）。
