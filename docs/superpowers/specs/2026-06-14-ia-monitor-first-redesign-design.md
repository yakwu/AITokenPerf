# 站点/监控信息架构重构：监控总览为主（设计）

- **日期**：2026-06-14
- **Issue**：#76
- **方案**：A（监控中心为主页）
- **修订**：v2（已纳入 3 个 subagent 审查结论 + 用户拍板的 4 项取舍）

## 1. 背景与问题

当前 IA 围绕"单次质量测试为主、定时监控为附加功能"搭建，但产品实际主功能已变为**定时拨测监控**。由此产生三处反人类的路径：

1. **新建断裂**：在 `/sites` 弹窗建好站点后，必须再点进该站点 → 找到「持续监控」tab → 单独建任务。"我想监控这个接口"被拆成两次独立操作。
2. **定时任务身份分裂**：它既是顶部导航的独立入口 `/tasks`（跨站点只读总览），又是站点详情里的一个 tab，用户分不清"监控属于站点还是独立的东西"。
3. **模型三处配置**：全局模型库（`/settings/models`）、站点绑定模型（站点·配置 tab）、任务级再选一遍（持续监控 tab），同一个模型要碰三个地方。

**根因**：信息架构仍是"单次测试为主"的旧心智模型，与"监控为主功能"的现实错位。

## 2. 设计目标

- 让"监控是主功能"在 IA 上立起来：一进门就是监控运行态。
- 两种用户都顺：①只想监控 ②想先单次测试再决定是否监控。主路径偏监控。
- 消除三处具体摩擦：新建断裂、任务身份分裂、模型三处配置。
- 可分阶段落地，控制改动风险。

## 3. 关键决策记录（本次拍板）

| 议题 | 决策 |
|------|------|
| 新建引导方式 | **表单内联勾选**「创建后立即开启监控（默认勾选）」，一步建好站点+监控，不用弹窗二次确认 |
| 告警展示去重 | **按站点×模型合并**：同一格子只一条，标注"所属 N 个任务" |
| 任务站点数 | **明确锁定单站点**（一任务=一站点） |
| 站点列表瘦身度 | **保留站点级健康摘要**（可用性点 + 成功率），详细 site×model 大表在监控总览 |
| 模型库与权限 | 全局库 = 管理员维护的价格/参考层；普通用户在站点配置内联新增 = 只绑到自己站点（不回写全局库） |

## 4. 非目标（YAGNI）

- 不引入告警"静音/snooze"功能（本次不做，监控总览不出现 `[静音]` 入口）。
- 不引入告警"已确认/ack"状态（多人协作处置闭环留待后续迭代）。
- 不改动告警评估算法（连续两轮防抖逻辑保持不变）。
- 不改动后端数据模型核心结构（`profiles` / `scheduled_tasks` 关联关系不变）。
- 不做模型库的权限体系重构。
- 不开发"批量开启监控/批量暂停"（站点量级有限，留待后续）。

## 5. 导航与路由

### 顶部导航

```
[监控总览]   [站点管理]   [历史与对比]        ⚙设置   👤用户
 ↑ / 默认着陆
```

`定时任务` 一词从顶导消失，升级为主着陆的 `监控总览`；`站点` 改名 `站点管理`，明确"看 vs 管"的语义对，退到第二位。

### 路由变化

| 路由 | 组件 | 说明 |
|------|------|------|
| `/` | （重定向） | → `/monitor`（原 → `/sites`） |
| `/monitor` 【新】 | `MonitorView.vue` | 监控总览/告警中心（运行态主着陆） |
| `/sites` | `SitesView.vue` | 站点管理区（保留站点级健康摘要） |
| `/sites/:id` | `SiteDetailView.vue` | 站点详情（tab 重排） |
| `/history` | `HistoryView.vue` | 不变 |
| `/tasks` | （前端路由重定向） | → `/monitor`（保留旧书签兼容） |
| `/settings/*` | 不变 | 模型库内容调整（见 §10） |

**关于 `/tasks` 重定向的纠正**：这是 **SPA 前端路由重定向**（client-side），不是 HTTP 301；保留它仅为兼容老用户的浏览器书签。原 spec 称"为飞书告警卡片跳转链接"——经核实 `build_feishu_card` 当前**无任何跳转链接**，该理由作废。反向地，本次将**给飞书卡片补上跳转链接**（见 §6），让告警能一键点进对应站点，这才是"监控为主"的真实闭环。

## 6. 监控总览 / 告警中心 `/monitor`（运行态主着陆）

定位：**看 + 运行控制，不做结构性编辑。** 一进门回答"我的监控现在健康吗？谁出事了？"

- **看**：健康总览、当前告警、任务跑批状态。
- **运行控制（可就地操作）**：暂停 / 恢复 / 立即跑。
- **结构性编辑（必须回站点）**：新建/修改任务（频率、模型、参数）、改连接信息。

页面结构（自上而下四块）：

1. **顶部状态条**：`🔴告警中 N  🟡降级 N  🟢健康 N  ⚪未测 N`，右侧时间范围 + 刷新。
   - **默认时间范围收窄到 1h/6h**（作为默认首页，避免 7d 全表扫描压力，见 §10）。时间范围复用全局 `timeRangeStore`，与站点详情/历史页一致。
2. **当前告警区**：展示**正在告警**的格子，**按站点×模型合并去重**。
   - 每条：站点×模型、成功率、连续轮次、所属任务（多任务时标注"所属 N 个任务"）、相对时间、`[进站点]`。
   - 无告警时收起成一行"✅ 一切正常"。
   - **数据来源需新建聚合端点**（见 §10）——`alert_state` 是任务私有 JSON，当前无 HTTP 出口。
3. **站点×模型健康总览**：复用站点健康看板（可用性柱状、成功率、TTFT、趋势、下次拨测）。
   - **前置：先把现 `SitesView` 内联的健康看板抽成独立组件 `SiteHealthBoard.vue`**（含排序/展开/收藏/CSS），供 `/monitor` 与 `/sites` 共用，避免复制粘贴产生两份会漂移的逻辑。
4. **监控任务跑批状态**：默认折叠区（任务名/站点/频率/上次结果/下次执行 + 暂停·恢复·立即跑）。

## 7. 站点管理区 `/sites`（管理态，保留健康摘要）

定位为"管理清单 + 轻量健康信号"，而非完整看板：

```
站点名       目标地址          模型数   健康      监控      操作
aihezu-aws   api.xxx.com/v1   3       🟢98%    🟢开     [进入→]
test-azure   azure.xxx.com    1       🔴42%    ⏸暂停    [进入→]
new-site     api.yyy.com      2       ⚪未测   ⚪关     [进入→]
```

- **保留**：站点名 / 目标地址 / 模型数 / **站点级健康摘要（可用性点 + 成功率）** / **监控开关状态** / 进入。可按健康/收藏排序、状态筛选（沿用现有能力的轻量版）。
- **移除**：每模型展开的详细柱状/趋势/TTFT 多列（详细 site×model 大表在监控总览）。
- **`监控` 列三态**（任务 status 仅 active/paused）：
  - `🟢开`：至少一个 active 任务；
  - `⏸暂停`：有任务但全部 paused；
  - `⚪关`：无任务。未挂监控的引导去开启。
- **新增派生字段**：`has_active_monitor` / 监控态需后端在 `get_sites_summary` 里补出（其内部已查 `get_scheduled_tasks`，数据在手边，仅需透出）。

## 8. 站点详情 `/sites/:id`：tab 重排

```
现在：[概览] [配置] [性能测试] [持续监控]
改为：[概况] [监控] [单次测试] [配置]
```

- 顺序调整：`监控` 提到第二、紧跟概况（主功能靠前）；`单次测试`（原"性能测试"）后移；`配置`（连接信息/Key）放最后（低频）。
- **`监控` tab**：原"持续监控"，本站点监控任务在此建/改/暂停——"配监控"的唯一正式入口。
- **`配置` tab**：连接信息（地址/Key/绑定模型/改名/删站点），低频维护。
- **默认 tab：保留现有"数据感知"逻辑**（`SiteDetailView` 现已实现：有数据落概况、无数据落测试/监控），**不写死概况**，避免新建空站点首屏是空表的回归。
- **清理存量 query 别名**：现有列表/任务行硬编码的 `?tab=trends`（映射到 overview）等需随重排一并清理，确保点进去落到预期 tab。tab 锚定用**名称**而非索引，避免老深链错位。

## 9. 新建站点 → 内联开启监控（一步到位）

放弃"创建成功弹下一步"模态（审查指出大概率被"以后再说"消解，反坐实 §1 的新建断裂）。改为**表单内联勾选**：

```
[+ 新建站点] 弹窗（连接信息）
  ├─ 站点名称 *
  ├─ 目标地址 *
  ├─ API Key *
  ├─ 绑定模型 *
  ├─ ☑ 创建后立即开启监控（推荐，默认勾选）
  │     └─ 勾选时展开极简监控项：频率（默认10分钟）、监控模型（默认=已绑定模型）
  └─ [创建]
        ↓ 提交：一步建好站点 +（若勾选）建好监控任务
```

- **勾选状态**：提交即一次性创建站点 + 监控任务，真正把"建站点"与"开监控"合一。
- **取消勾选**：只建站点；留在站点详情概况页，顶部挂常驻提示"尚未开启监控 → 一键开启"。
- **存量站点**：已建但未挂监控的站点，同样在概况页顶部显示"一键开启监控"提示（不依赖新建流程触发）。
- **监控默认值的安全性**：频率默认 10 分钟；监控模型默认全选已绑定模型；**并发取安全低默认**（避免站点绑定大量模型时一次造出高并发拨测任务，结合真实量级保守取值，具体值实现阶段定）。

## 10. 模型配置归并（三处 → 一处定义）

| 层 | 角色 | 谁维护 |
|----|------|--------|
| 全局模型库 `/settings/models` | **价格/参考层**：模型清单 + 输入/输出单价（算成本用） | 管理员（普通用户无权进入） |
| 站点·配置 tab | **唯一定义层**：本站点服务哪些模型，选一次 | 用户（普通用户内联新增 = 只绑到自己站点，不回写全局库） |
| 监控任务 / 单次测试 | **勾选层**：从站点已绑定模型里勾子集，默认全选 | 用户 |

- **核心规则**：模型只在站点配置层认真定义一次；任务与单次测试退为"从站点模型勾选，默认全选"。
- **改动点**：任务层（`SiteSchedulesTab.vue`）当前是**自己手写的 combobox**（非 `ModelSelector`），其 `filteredCreateModels` 已只从站点模型筛选（方向已对一半），但仍保留 `addCreateModel/addEditModel` 允许输入站点没有的模型 ID——本次**砍掉这两个内联新增入口**（想加模型回站点配置加）。
- **权限澄清**：全局库 admin-only 不变；普通用户站点配置内联新增的自定义模型仅绑定在其 profile（无全局价格 → 成本列留空或标"未知价格"）。

## 11. 数据流与后端影响

- **数据模型不变**：`profiles`（站点）与 `scheduled_tasks`（任务，本次约束 `profile_ids` 恒为单元素）关联关系保持。
- **需新建/调整的后端能力**（不改表结构）：
  1. **当前告警聚合端点**（如 `GET /api/alerts/active`）：解开所有任务的 `alert_state`、筛出 `s=alerting` 的格子、按站点×模型合并、关联站点名 —— 阶段一必做项。
  2. **`get_sites_summary` 补 `has_active_monitor`/监控态**（数据已在手边，仅透出）。
  3. **可用性查询聚合下推**：`get_cell_availability_series` 当前是"取时间窗内全部 results 行进 Python 分桶"（无 LIMIT/无聚合），作为默认首页主数据源需做 SQL 侧聚合或收窄默认窗口，避免重演 #25/PR27 的全表加载问题。
  4. **飞书卡片加跳转链接**（`build_feishu_card`）：指向对应站点（或 `/monitor`），实现手机端一键定位。

## 12. 错误处理与边界

- `/tasks` 前端路由重定向→`/monitor`；飞书卡片改为带站点链接。
- **空态分级**：①无站点（去创建）②有站点无监控（去开启）③**有站点有任务但首次拨测未跑（next_run 未到）**——顶部计数计入"⚪未测"，健康表显示"等待首次拨测"，告警区不报。
- 新建内联"开启监控"时若站点无可用模型，给出提示而非创建空任务。
- 站点删除：单站点约束下，删站点 → 其关联任务一并删除（沿用现有级联，单站点无歧义）。
- `监控` 列 paused 第三态按 §7 显示 `⏸暂停`。

## 13. 迁移与存量数据

- **tab 重排**：按名称锚定 + 清理 `?tab=trends` 别名，存量深链尽量平滑；无法映射的旧别名回退到默认 tab。
- **模型归并**：存量任务 `configs_json.models` 可能含"站点未绑定"的模型（旧任务层自定义新增的）。迁移策略：**保留任务现有 models 不强制清除**（不破坏在跑的监控），但在任务编辑界面对"站点已无此模型"的项给失效标记 + 引导回站点绑定；新建/编辑时只能从站点模型勾选。
- **单站点约束**：核查存量是否存在 `profile_ids` 多元素的任务（UI 历来单站点，预期没有）；若有，迁移阶段记录并人工确认，不静默丢弃。
- **存量未挂监控站点**：概况页常驻"一键开启监控"提示覆盖。

## 14. 测试策略

- **E2E**：①新建站点时勾选"立即开启监控"→ 一步建好站点+任务；②`/tasks` 重定向到 `/monitor`；③监控总览展示合并去重后的告警 + 健康表；④站点详情 tab 顺序与数据感知默认 tab；⑤站点列表健康摘要 + 监控三态列。
- **单元/组件**：当前告警聚合端点的"按站点×模型合并、多任务标注 N"；`SiteHealthBoard` 抽离后两页渲染一致；模型勾选默认全选 + 砍掉任务内联新增；监控三态（active/paused/无）。
- **回归**：迁移并复用现有 `/sites` 看板与 `/tasks` 既有测试。

## 15. 落地阶段（实现计划阶段细化）

每阶段结束产品都应处于"可用、可发布"状态。

1. **阶段 1a（后端+组件前置）**：抽离 `SiteHealthBoard.vue` 组件；新建当前告警聚合端点；可用性查询聚合下推/收窄窗口。
2. **阶段 1b（监控总览成形）**：组装 `MonitorView`（四块）；`/` → `/monitor`、`/tasks` → `/monitor` 重定向；飞书卡片加链接。
3. **阶段 2（站点区）**：站点列表保留健康摘要 + 监控三态列；站点详情 tab 重排（保留智能默认 + 清理 query 别名）。
4. **阶段 3（新建合一）**：新建站点表单内联"立即开启监控"勾选；存量站点概况页常驻引导。
5. **阶段 4（模型归并）**：砍任务层内联新增模型；存量模型迁移标记；权限层校验。
