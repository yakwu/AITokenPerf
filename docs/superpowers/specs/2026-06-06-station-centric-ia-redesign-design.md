# 站点中心化信息架构重构（站点 → 模型 → 三类测试）

- **日期**: 2026-06-06
- **状态**: 设计待评审
- **主题**: 信息架构（IA）破坏性重构，第一目标是易用性
- **关联**: 这是「监控体验优化」分析里的 P0-1 主题。告警升级、动态基线、统一诊断套件是另外的主题，本次只预留入口、不实现。

---

## 1. 背景与问题

AITokenPerf 是面向大模型 API 的主动拨测监控平台。当前前端把**同一份数据**摆成了多个割裂页面，概念重叠，用户（运维使用者、非深度后端）容易迷路。

已核实的事实：

- 数据库**没有 `sites` 表，只有 `profiles` 表**。`/sites`（站点）的"新建站点"和 `/config`（连接配置）的"保存配置"**都 POST 到同一个 `/api/profiles/save`**，建出来是一模一样的行。
- `/api/sites/summary`、`/api/sites/trend` 内部都用 `profile_name`。"站点"就是 profile 的展示别名。
- 定时任务有**两个创建入口**（`/tasks` 全局页 + 站点详情里的 tab），两个表单字段不同步，但都走 `/api/schedules`。
- 模型有三处概念重叠：模型库（全局价格字典）、"我的模型"（中间层）、站点自己的 `models` 列表。
- "单次拨测"把**两种语义完全不同的测试**混在一个表单：低并发探活式验证 vs 高并发压测。

### 用户的真实心智模型

```
站点（渠道 = base_url + key）
   └── 多个被测模型（opus4.7 / opus4.8 / sonnet4.6 … 随新模型发布动态增删，如 opus4.9）
          └── 对站点+模型做三类测试
```

用户对一个站点要做的是**三类目的不同的测试**：

| 测试类型 | 目的 | 并发 | 触发 | 最关注 | 告警 |
|---|---|---|---|---|---|
| 准入测试 | 新站点/新模型能不能用、值不值得接 | 低（1） | 手动一次 | 连通性、TTFT、成功率、输出合理性 | 否 |
| 多并发压测 | 容量上限、性能拐点 | 高（梯度 1→10→50→100） | 手动一次 | 各并发下的延迟/吞吐/成功率曲线 | 否 |
| 持续连续性 | 长期稳定性、基础性能退化 | 固定低并发（1~2） | 定时自动 | 趋势、退化检测、成功率 | 是 |

## 2. 设计目标与非目标

### 目标（按优先级）

1. **易用性第一——查看场景和配置场景同等重要**。每个配置动作都要更少步骤、更少跳转、更合理默认。高频动作（加新发布模型、加完顺手开定时拨测）必须顺手。
2. **概念去重**：一个数据实体一个页面，消除"站点/连接配置/模型库"的重叠与"定时任务"的双入口。
3. **测试语义分离**：把准入 / 压测 / 持续监控拆成三个目的清晰的入口，历史与趋势不再混看。

### 非目标（本次不做，避免范围膨胀）

- 不做告警升级（延迟/环比告警、状态机去抖）——另一个 P0 主题。
- 不做动态基线着色——另一个 P0 主题。
- 不实现统一诊断套件——已有独立设计，本次只在准入测试里预留"诊断"展示位。
- 不改指标计算逻辑（TTFT/TPOT/E2E 算法不动）。
- 不改 `profiles`、`results` 表的既有结构与既有历史数据语义（只新增一列，见 §6）。

## 3. 目标信息架构

### 顶层导航：9 项 → 5 项

| 新导航 | 说明 | 来自 |
|---|---|---|
| 📊 概览 | 全局健康快照 + **全局任务只读总览** | 原 `/`，吸收 `/tasks` 的全局视图 |
| 🌐 站点 | 唯一的渠道管理与测试中心 | 原 `/sites` + `/sites/:id` |
| 🕑 历史 | 全局检索 + 对比 + 诊断 | 原 `/history`，不动 |
| 📦 模型库 | 纯价格参考字典 | 原 `/models`，砍掉"我的模型"中间层 |
| ⚙️ 设置 | 个人设置 + 管理员 | 原 `/settings` + `/admin-users` |

**删除**：`/config`（连接配置页，与站点重复）。
**降级**：`/tasks` 独立创建入口取消，定时任务的创建/编辑统一回站点详情；全局"所有站点的持续监控任务"以**只读总览**形式并入概览（可跳转回站点编辑）。

### 站点详情：按测试目的分 tab

```
站点详情 · A站点   [🟢健康 · base_url · 3个模型 · 切换站点▾]
├─ 概况          ← 默认落地：本站点各模型的健康快照
├─ 🩺 准入测试    ← 选模型 · 并发1 · 跑一次 · 出"能不能用"体检报告
├─ 🔥 压测        ← 选模型 · 并发梯度 · 跑一次 · 出容量曲线
├─ 📈 持续监控    ← 选模型 · 固定低并发 · 定时 · 趋势 + 退化 + 告警
└─ 设置          ← 连接信息(base_url/key) + 模型清单增删(加 opus4.9 在这)
```

模型不是独立 tab，而是**每种测试里"选测哪些模型"的维度**；模型清单的增删收在「设置」。

## 4. 各 tab 详细设计

### 4.1 概况（默认落地页）
- 进站点先回答"现在健康吗"：各模型一行，显示 TTFT P50 / 出字速度 / 成功率 / 最近一次结果时间 / 是否有持续监控在跑。
- 顶部站点身份条 + 站点切换下拉（沿用现有 `SiteDetailView` 的切换器）。
- 每行可快捷跳到"对该模型做准入/压测/看趋势"。

### 4.2 准入测试 🩺
- **用途**：接入新站点或新模型时，快速判断"值不值得用"。
- **输入**：选 1~N 个模型；其余参数全部预设（并发=1，少量请求，标准 prompt）。**目标是"一键体检"，几乎不用填**。
- **输出**：一张体检报告卡——✅能否连通、TTFT、成功率、平均输出 tokens、输出是否合理（非空/长度达标）。为后续诊断套件预留展示位。
- 复用现有 `client.py` 单次请求采集逻辑，不新增测量代码。

### 4.3 压测 🔥
- **用途**：看站点容量上限、性能拐点。
- **输入**：选模型；并发梯度（预设 1→10→50→100，可改）；模式 burst/sustained。
- **输出**：容量曲线——X 轴并发，Y 轴 TTFT P50/P95、吞吐、成功率，看哪个并发开始变慢/掉成功率。
- 复用现有多并发执行逻辑（`run_burst`/`run_sustained`）。

### 4.4 持续监控 📈
- **用途**：长期盯稳定性与基础性能。
- **输入**：选模型；频率；固定低并发。**易用性要点**：从「设置」加完模型可顺手"加入持续监控"，自动带默认频率，不跳转重配。
- **输出**：趋势图（按测试类型与并发隔离，避免与压测数据混画）+ 最近运行 + 告警状态。
- 这是唯一会触发告警的测试类型；告警配置沿用现状（webhook+阈值），告警升级是后续主题。

### 4.5 设置 ⚙️
- 连接信息：base_url、api_key（脱敏显示）、协议/厂商。
- 模型清单增删：搜索模型库即加（输入 `opus4.9` → 匹配 `claude-opus-4-9`(带价格) → 加入）；找不到有"自定义模型"兜底。
- 删除站点。

## 5. 配置场景易用性要求（一等需求）

实现时把以下当作硬性验收点：

1. **加新模型 ≤ 3 步**：设置→搜索→加入；加入时可勾"同时加入持续监控"。
2. **建站点字段最小化**：必填只留名称、base_url、key、至少一个模型；其余给默认。
3. **测试不用填一堆参数**：准入几乎零配置；压测给预设梯度；持续监控给默认频率。
4. **不跨页面找配置**：一个站点的所有配置都在它的详情页里，不再去 `/config`、`/tasks` 之间跳。
5. **改动有反馈**：保存/加入/启停都有即时状态提示。

## 6. 数据层改动（唯一的数据库改动）

准入测试与压测在系统里都是 `source=manual`，仅靠 `mode`/`concurrency` 无法稳定区分。新增一列标识测试类型。

- 在 `results` 表新增 `test_kind TEXT`，取值 `admission` / `stress` / `continuous`。
  - SQLite 与 PostgreSQL 两套建表语句同步新增（`app/db.py`）。
  - 写入：`db.save_result()` 落该字段；由发起测试的入口决定取值。
  - **回填**：老数据 `test_kind` 为空 → 视为 `legacy`，按 `source` 推断展示（`scheduled`→持续监控，`manual`→历史里归到"未分类/压测"）。不强制重写历史行。
- 历史页 `/history` 与站点趋势：增加按 `test_kind` 过滤；趋势图默认只画同一 `test_kind`（且持续监控锁定并发）以防失真。
- `profiles` 表结构**不变**。

## 7. 受影响范围

### 前端（frontend/src）
- 路由（`router.js`）：删 `/config`；`/tasks` 改为只读总览或并入概览；`/admin-users` 收进设置。
- 删/改页面：`ProfileView.vue`（删，逻辑并入站点设置）、`TasksView.vue`（改只读）、`ModelsView.vue`（砍"我的模型"tab）。
- 站点详情：`SiteDetailView.vue` 的 tab 重组；现有 `SiteTestTab.vue`（1401 行，过大）**拆成** `AdmissionTestTab` 与 `StressTestTab` 两个聚焦组件；`SiteSchedulesTab.vue` → 持续监控 tab；`SiteConfigTab.vue` → 设置 tab（吸收连接信息+模型增删）。
- 概览：`DashboardView.vue` 增加全局任务只读总览区块。
- 历史/趋势：`HistoryView.vue`、`SiteTrendsTab.vue` 增加 `test_kind` 过滤与隔离绘制。

### 后端（app）
- `db.py`：两套 schema 加 `test_kind` 列；`save_result()` 写入；查询支持按 `test_kind` 过滤。
- `server.py`：发起测试的入口接收/透传 `test_kind`；`/api/profiles*`、`/api/schedules*` 保留；`/api/sites/*` 保留。
- 指标计算（`client.py`/`stats.py`）：不动。

## 8. 迁移与兼容

- 用户已授权破坏性重构（页面层）。**数据层非破坏**：profiles/results 既有数据保留，只新增一列且可空。
- 路由删除：`/config`、`/tasks`（旧创建态）做重定向到对应新位置，避免书签 404。
- 分阶段上线（见 §10），每阶段可独立部署、独立回滚。

---

## 9. 测试策略

- 后端：`test_kind` 列读写、按 `test_kind` 过滤查询、老数据回填推断的单测（沿用 `tests/` pytest）。
- 前端：站点详情 tab 切换、加模型≤3步、准入零配置可跑通、趋势按 `test_kind` 隔离的 E2E（沿用 Playwright）。
- 回归：历史/对比/诊断功能不受影响；pre-push 的 vitest + build 通过。

## 10. 分阶段实现建议（每阶段一个 PR）

1. **阶段一 · 导航与页面收敛**：删 `/config`、`/tasks` 改只读、`/models` 砍中间层、导航 5 项、旧路由重定向。（纯前端，风险低，先止血）
2. **阶段二 · 数据层 test_kind**：`results` 加列 + 写入 + 回填 + 历史/趋势按类型过滤隔离。（前后端，含迁移）
3. **阶段三 · 站点详情按测试目的重组**：`SiteTestTab` 拆成准入/压测，持续监控与设置 tab 落位，落实 §5 配置易用性验收点。（改动最大，压轴）
