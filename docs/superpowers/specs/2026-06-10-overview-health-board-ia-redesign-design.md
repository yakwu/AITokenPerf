- **日期**: 2026-06-10
- **状态**: 设计待评审
- **主题**: 信息架构（IA）重构，第一目标是"一目了然的监控总览"与"看数据不再散落"
- **关联**:
  - **取代** `2026-06-06-station-centric-ia-redesign-design.md` 中**未落地的导航级决策**（概览/目标站点分开、配置留头像下拉），见 §4。

## 1. 背景与问题

AITokenPerf 是面向大模型 API 的主动拨测监控平台（站点 = 渠道 = `profiles` 行；站点下挂多个被测模型）。用户（运维使用者、非深度后端）反馈**整个平台 IA 混乱**，最痛的是：

1. **「概览」不像概览**——现状是"统计卡片 + 活动流水"，无法一眼看清所有站点×模型的健康与趋势，不像主流监控平台的总览盘。（用户原话锁定的第一痛点）
2. **看数据散落 3~4 处**——站点健康在「概览」看一遍、「目标站点」又看一遍；历史趋势在站点「概况」里、跨站点对比在「历史」里。
3. **配置入口藏在头像下拉**——「模型管理」「用户管理」在右上角头像里且**仅管理员可见**（`App.vue:28,32` 带 `v-if role==='admin'`），难发现。
4. **定时任务双入口**——顶栏「定时任务」与站点详情「持续监控」操作同一批对象，定位含糊。
5. **告警渠道埋得更深**——它不是头像下拉的独立项，而是**嵌在 头像→个人资料(`SettingsView.vue:58`)页内的一个区块**里。配监控告警时若没渠道，得离开当前站点跳到个人资料页里找告警器，建完再回来。

### 根因：上一轮 IA 重构没收尾

`2026-06-06` 的「站点中心化 IA 重构」诊断了同样的问题并给了方案，但**只落地了一半**：

- **已落地（PR#36 等）**：站点详情按 4 tab 组织（概况/测试/持续监控/设置）、持续监控表单瘦身、站点收藏、删掉隐藏的 `/config` 孤儿页。
- **未落地**：顶栏「定时任务」未降级、「概览」与「目标站点」未收敛、「测试」tab 未拆体检/压测、`test_kind` 未加。

于是平台停在"半重构"状态 —— 这正是现在仍然乱的原因。同时近期 #48~#56 大力投入**按模型/按格子**看数据，与本设计的"站点→展开模型→逐格可用性"方向**高度一致、可直接复用**。本设计的任务就是**给 IA 收尾，并把概览升级成真正的监控看板**。

## 2. 设计目标与非目标

### 目标（按优先级）

1. **概览 = 一目了然的「站点×模型健康看板」**：异常自动置顶，每个站点一行（聚合），可展开看各模型，带状态页式"可用性历史柱"与延迟趋势。
2. **消除"看数据散落"**：把「概览」与「目标站点」**合并成单一「站点」页**（看板即列表，行内可操作、点行下钻详情）。
3. **配置可发现**：把模型库 / 告警渠道 / 用户管理 从头像下拉**迁到顶栏 ⚙设置 hub**。
4. **顺畅主线**：建站 → 测试 → 持续监控 → 告警，其中**告警渠道可在配监控时就地新建**，不跳走。

### 非目标（避免范围膨胀）

- **不做**三类测试（体检/压测/持续监控）语义拆分与 `test_kind` 数据列——属 06-06 的另一条独立线，本次不碰；看板只用现有数据，不依赖 `test_kind`。
- **不改**压测引擎与指标算法（TTFT/TPOT/E2E），**不改** `profiles`/`results` 表结构。
- **不做**告警升级（延迟/环比告警、去抖）与动态基线着色（延续既有非目标）。
- **不重写后端架构**（真实量级约 100 并发 + 几十拨测；不引入多 worker/Rust/Go 重写）。

---

## 3. 设计原则

1. **"不可用是常态"，用聚合反映水位、不用异常驱动**。这些第三方/中转 AI 接口经常超时、限流、部分模型挂，若"任一模型异常就把站点标红/报警"，看板会长期一片红、告警疲劳。因此站点行取**各模型平均**，可用性柱按**平均成功率**着色；**明确放弃**"有一个坏模型就把站点标红"的兜底（用户已确认）。
2. **一个实体一个家**：站点状态只在「站点」页呈现，不再多处重复。
3. **看（监控）与管（配置）分层但相连**：看板是只读监控主场；管理动作（建站/测试/配监控/改设置）行内触发或下钻详情，路径短。

## 5. 「站点」页（本次核心）

合并 `DashboardView` 与 `SitesView` 为单一「站点」页，默认呈现**健康看板**。

### 5.1 健康看板（默认视图）

**列结构**（紧凑表，方案 B）：

| 健康点 | 站点 / 模型（可展开） | 可用性 · 近 N | TTFT P50 | 趋势(7d) | Token/s | 成功率 | 最近测试 |
|---|---|---|---|---|---|---|---|

- **两层结构**：默认**一行一个站点**（聚合），点 ▸ 展开为该站各模型子行（各有自己的可用性柱与指标）。
- **聚合 = 平均**：站点行的 TTFT/成功率/可用性柱均为各模型**平均**（标注"平均"）。
- **三档健康前端现算**：看板要红/橙/绿三档，但后端 `get_sites_summary` 的 `health` 只有 healthy/error **二档**（`db.py:1707-1720`，取最近 5 条均值）。因此**橙档由前端按成功率阈值现算**（见着色阈值），不依赖后端 `health` 字段；站点健康点同样由"平均成功率 + 阈值"落档。
- **默认全部收起**，**不记忆**手动展开状态（用户已确认）。
- **可用性历史柱**（状态页风格）：一排小竖柱，**每柱 = 一个时间桶**（非"每次执行"，理由见 §9.1），按该桶成功率着色 —— **绿 ≥95% / 橙 80–95% / 红 <80%**（阈值可配）；hover 显示该桶时间区间 + 成功率。桶数/桶宽由顶栏全局时间范围派生（如所选窗口均分 24 桶），从而与时间 pills 语义统一。
- **渲染量级**：站点行的柱用各模型同一时间桶的成功率求平均；模型行的柱只在该站**展开时**才渲染（默认收起 → 首屏只画站点行的柱 + sparkline，约 10~30 行，可控）。
- **排序**：异常/低可用置顶（需先算全量再排序）；**收藏置顶**沿用 PR#36 已有的站点收藏（`SitesView.vue:220-267`）；健康站点可折叠明细。
- **全局健康条**：顶部 `异常 N · 健康 N · 未测 N`。
- **工具栏**：🔍搜索（名称/地址） · 状态筛选 chip · **＋新建站点**；顶栏**全局时间范围 pills** 仍生效（驱动看板数据窗口）。
- **行内操作**：一键测试 · 详情→；点任意行 → 进站点详情。
- **不做兜底标红**（§3 原则）；"该报就报"由 #56 逐格告警覆盖。

### 5.2 取代与保留

- **取代**：`DashboardView`（概览）内容并入看板后退役；顶栏不再有独立「概览」入口；`/`（原概览）与 `/sites` 合并到「站点」。
- **保留**：站点详情页（概况/测试/持续监控/设置）结构不变。由于顶栏不再叫"概览"，详情里的「概况」tab **不再重名**——痛点中的命名撞车自动消除。

### 5.3 数据来源（后端需结构性扩展，**非小改**）

> ⚠ 修订：原稿低估了后端工作量，已据代码核实更正。

**现状（`get_sites_summary`，`db.py:1614-1749`）只产出**：站点级 `health`（最近 **5 条**成功率均值，二档）+ `latest_results`（仅 `prows[:5]`）+ `sparkline_data`（TTFT P50 时间序列）。**per-模型指标并不在后端**，是前端 `getModelMetrics`（`siteMetrics.js:6`）在这 5 条上**现算**的。5 条样本**画不了"近 24 桶"可用性柱**。

**可复用的**：
- 前端 `siteMetrics.js` 现有的 per-模型指标/sparkline 计算（首屏数字仍可用现有 summary）。
- #56 `get_run_success_rate_by_cell`（`db.py:846`）的**分组口径**——按 `(profile_name 规范列, config.model)`、缺失模型归 `-`。**仅口径可借鉴，函数本身不可复用**：它入参是 `run_ids`、只聚合**单轮**、且把一轮所有并发档累加成**一个数**，给不出"近 N 桶的逐桶序列"。

**必须新增（后端）**：
- 一个**按 (站点 profile, 模型) 在所选时间窗内分时间桶聚合成功率**的查询/端点（输出 `{(profile,model): [桶1成功率, 桶2成功率, ...]}`），供可用性柱使用。可作为独立新端点，或扩展 `sites/summary`；**这是本设计后端的主要工作量**（见 §10 阶段零）。
- 站点行的柱 = 同一时间桶内各模型成功率求平均（共享时间轴，见 §9.1）。

**前端**：可用性着色 / 平均聚合 / 排序逻辑放**纯函数**（`siteMetrics.js` 扩展），便于 vitest 单测；不新增测量代码。

## 7. 定时任务澄清（②）+ 告警就地新建（③）

- **定时任务（顶栏）**：跨站点的**只读总览 + 轻操作**（暂停/恢复/立即跑/改频率）。默认按站点折叠或只显示异常任务，避免几十条变一面墙。**不在此创建**。

## 9. 开放问题（已给默认）

1. **可用性柱 = 时间桶（已据审计定案，非"近 N 次执行"）**：原稿曾默认"近 24 次执行"，但审计指出按执行对齐有缺陷——不同模型拨测频率不齐，"第 i 近执行"会把不同时刻拼到同一根柱、横轴失去时间意义，站点行更无从平均。**故改为时间桶**：在所选时间窗内均分 **N 个桶（默认 24）**，每桶取该 (站点,模型) 落在桶内拨测的成功率着色；**站点行第 k 桶 = 各模型第 k 桶成功率的平均**（共享时钟轴，天然可平均）。
   - **附带解决**了"时间 pills 按时间、可用性柱按次数"的窗口冲突——柱与全局时间范围统一到同一时间轴。
   - 空桶（该段无拨测）显示为灰/空，不计入平均；桶宽随所选窗口缩放（如 1h 窗 → 桶更细，30d 窗 → 桶更粗）。
2. **着色阈值**：绿 ≥95% / 橙 80–95% / 红 <80%。**默认**采用，设为可配。
3. **⚙设置入口形态**：右侧 gear 图标 vs 也给文字 tab。**默认**：gear 图标。
4. **定时任务最终是否并入站点页一个区块**（06-06 思路）：**默认**先保留独立 tab，后续可再评估并入。
5. **原概览的"最近活动流水 / 异常告警"区块去向**：`DashboardView` 还用 `getResults(limit 1000)` 画最近活动流水、用 `getSchedules` 画告警区（`DashboardView.vue:160,456`）。合并到看板后，**默认不保留通用"最近活动"长流水**（其能力归「历史与对比」）；异常面由看板顶部全局健康条 + 异常置顶覆盖。若仍需"最近告警"，后续作为看板上方一个紧凑区块再加，**不在阶段一**。
